# Notifications (Frontend Integration)

Notifications are **polling-based** (no WebSocket push). The UI should poll for unread counts and optionally fetch the latest notifications when the count increases.

All endpoints below require:

- Header: `Authorization: Bearer <access_token>`
- Response wrapper:
  ```json
  { "success": true, "message": "…", "data": { }, "errors": null }
  ```

---

## 1) Fast badge/toast polling (recommended)

**Endpoint**

- `GET /api/v1/notifications/unread-count/`

**Success response**

```json
{
  "success": true,
  "message": "Success",
  "data": { "unread_count": 3 },
  "errors": null
}
```

**Suggested UI behavior (“popping”)**

1. Poll every **10–30 seconds** and also on app focus / app resume.
2. Keep the last seen value (e.g. `lastUnreadCount`).
3. If `unread_count` increases, show a toast/snackbar:
   - “You have new notifications” → action “View”
4. Optionally fetch the latest unread list immediately:
   - `GET /api/v1/notifications/?is_read=false&page=1&page_size=20`

---

## 2) List notifications (screen/feed)

**Endpoint**

- `GET /api/v1/notifications/`

**Query params**

- `is_read=true|false|all` (default: `all`)
- `type=<notification_type>` (optional, exact values listed below)
- Pagination:
  - `page` (default DRF pagination)
  - `page_size` (default `20`, max `100`)

**Success response shape**

This endpoint returns a paginated payload inside the standard wrapper. The `data` object includes both pagination keys and `unread_count`:

```json
{
  "success": true,
  "message": "Retrieved 12 notifications",
  "data": {
    "count": 12,
    "next": null,
    "previous": null,
    "results": [
      {
        "id": 10,
        "notification_type": "share_request",
        "content": "John Doe shared \"Assignment.pdf\" with you",
        "related_object_id": "3d97c2df-9a32-4298-98a9-7f309035977e",
        "is_read": false,
        "created_at": "2026-04-09T10:00:00Z"
      }
    ],
    "unread_count": 3
  },
  "errors": null
}
```

Notes:

- Ordering is newest-first (`created_at` descending).
- `related_object_id` is **always a string** (even when it represents an integer id).

## 3) Mark as read

### Mark one notification as read

- `POST /api/v1/notifications/{id}/read/`

Success: returns the updated notification object (wrapped).

### Mark all as read

- `POST /api/v1/notifications/read-all/`

Success response:

```json
{
  "success": true,
  "message": "Marked 7 notifications as read",
  "data": { "marked_read": 7 },
  "errors": null
}
```

---

## 4) Delete a notification

- `DELETE /api/v1/notifications/{id}/`

Success response:

```json
{
  "success": true,
  "message": "Notification deleted successfully",
  "data": null,
  "errors": null
}
```

## Notification types + what `related_object_id` points to

These are the types currently generated by the backend:

- `share_request` → `related_object_id = <share_id>` (UUID string) from `POST /api/v1/sharing/`
- `share_accepted` → `related_object_id = <share_id>` (UUID string) from `POST /api/v1/sharing/{share_id}/accept/`
- `share_rejected` → `related_object_id = <share_id>` (UUID string) from `POST /api/v1/sharing/{share_id}/reject/`
- `friend_request` → `related_object_id = <friendship_id>` (integer id as string) from `POST /api/v1/friends/add/`
- `friend_accepted` → `related_object_id = <friendship_id>` (integer id as string) from `POST /api/v1/friends/{id}/accept/`
- `upload_created` → `related_object_id = <upload_id>` (UUID string) from `POST /api/v1/uploads/`
- `class_joined` → `related_object_id = <class_id>` (UUID string) from `POST /api/v1/classes/join/`

Frontend routing examples:

- `share_*` → open your “Shares” screen and highlight that share id
- `friend_*` → open “Friends / Requests”
- `upload_created` → open “Uploads” (optionally filter by class) and highlight that upload id
- `class_joined` → open class members screen for that class id

## Caching / Redis notes (important for polling)

- Notifications endpoints use the project cache layer (namespace `notifications`) with a short TTL.
- When `REDIS_URL` is configured server-side, responses are cached in Redis; otherwise they use in-memory cache.
- Cache is invalidated automatically when notifications are created or marked read, but you should still treat polling results as “near real-time”, not instant.
